# Identity spike: results

**Verdict: the design of [docs/design/identity.md](../../docs/design/identity.md) works end to end against a real OpenID Connect provider and a real sshd, with the standard library alone for the token check.** A person signed in by the loopback flow, by a printed URL with the address pasted back, by the provider's code page and by the device grant; each time the server checked the ID token (signature, issuer, audience, expiry, `auth_time`, and the nonce that commits to the new key) and answered with the line it would write to its keys file. A real sshd admitted that line and, past its end, refused it. A workload token from a client-credentials grant went through the same verifier and a trust rule mapped it to a service principal. Three findings change the design: sshd reads `expiry-time` in the server's own zone unless the value ends in `Z`; with the provider's browser session open, a sign-in completes with nobody seeing a page unless `prompt=login` is sent; and Keycloak returns a nonce sent with a device grant, which RFC 8628 does not promise and Dex did not do.

15 October 2026. Code: this directory, a Go module of its own (`go.mod`), so the main module and its gate are untouched.

| Path | What |
|---|---|
| `jose/` | Compact JWS parsing and RS256 and ES256 verification, and JSON Web Keys, on the standard library; table tests and a fuzz target |
| `oidc/` | The verifier: discovery, the key set cached and refetched at most once a minute, the claim checks; tests against a fake issuer on a fake clock |
| `trust/` | Trust rules for workload tokens; table tests |
| `cmd/spike/` | The client and a stand-in for the server's enrollment (`login`, `workload`), Keycloak's realm made by its admin API (`setup`), and the sshd checks (`sshkeys`, `probe`, `hold`). A stand-in browser fills Keycloak's forms; it is not part of the design |
| `sshd/` | An sshd image with the server guide's `Match` block, in a zone chosen at start |
| `run.sh` | Runs all of it in throwaway containers and removes them, and the images it pulled |

To rerun, with Docker and Go on `PATH`: `spike/identity/run.sh STATE_DIR`, with a directory that does not exist yet; it holds the generated passwords, the client secret and the keys (each 0600), none of which is printed. Delete it afterward. `go test ./...` from this directory runs the unit tests with no containers.

## 2. People signing in

Each mode made a new ed25519 key, took a challenge from the stand-in server, sent the nonce `base64url(SHA-256("aries-login-v1" ‖ 0 ‖ challenge ‖ 0 ‖ public key))`, signed in as alice with the stand-in browser, exchanged the code with its PKCE verifier, and handed the ID token and the public key to the stand-in server.

| Mode | What the person handles | Result |
|---|---|---|
| Loopback (`http://127.0.0.1:PORT/callback`, a listener) | A URL of 372 characters, opened for them | Signed in; ID token ES256, 898 bytes, `aud` `aries-cli`, `azp` `aries-cli`, 5-minute lifetime, `auth_time` present, **nonce returned and equal**, `email_verified` true. Enrolled as alice, the invitation bound |
| URL, the address pasted back (redirect to `127.0.0.1` where nothing listens) | The same URL; then the address the browser could not open, **265 characters**, pasted back. The client checked its `state` | The same |
| URL, the provider's code page (`urn:ietf:wg:oauth:2.0:oob`) | A URL of 366 characters; then a **98-character code** from Keycloak's page | The same |
| Device grant | A 9-character user code at `/realms/aries-spike/device`; `verification_uri_complete` offered; 600 s to finish, polled every 2 s | Signed in after one `authorization_pending`. **The nonce sent with the device authorization request came back in the ID token, equal.** A second poll with the same device code: `invalid_grant: Device code not valid`, so the code is single use |

Checks against the same token, by the stand-in server:

| Tried | Result |
|---|---|
| The token, with another public key and a fresh challenge (a thief who holds the token) | Refused: the nonce does not match |
| The token again, with the same key and a fresh challenge (a replay) | Refused: the nonce does not match |
| The device grant's token again (handled as unbound, accepted once) | Refused: already used |
| bob, who has an identity at the provider and no invitation | Refused by the server: no invitation |
| A code exchanged with a PKCE verifier other than the one committed to | Refused by Keycloak: `invalid_grant: PKCE verification failed: Code mismatch` |

**Signing in again in the same browser** (the loopback mode, after its first sign-in):

| Request | Pages the person saw | `auth_time` | Server |
|---|---|---|---|
| The same request with `max_age=600` | **None**: Keycloak redirected straight back | Unchanged from the first sign-in | Enrolled (the identity matched by subject, not bound again) |
| The same with `prompt=login` | The sign-in page | The new sign-in's | Enrolled |

So `max_age` alone does not make a second sign-in within it visible to the person, and a tool that opens the URL in a browser whose session is open renews with nobody present. `prompt=login` forces the page. This is what makes the design send `prompt=login` where the provider honors it and check `auth_time` (identity.md §6.7).

**Keycloak's quirks met:**

- The client's PKCE requirement applies to its device grant as well: without `code_challenge` the device authorization request is refused (`Missing parameter: code_challenge_method`), and with it the poll must carry `code_verifier`. RFC 8628 has no PKCE.
- Polling before the interval answered `slow_down` (run 2); the client then waits five seconds more, as RFC 8628 §3.5 says.
- `http://127.0.0.1/*` as a redirect admitted every port the client chose.
- The key set holds an RSA key marked `"use":"enc"` beside the signing keys; the verifier skips it.

## 3. A service principal

`spike workload` asked Keycloak for a token by the client-credentials grant, standing in for a platform's workload token.

| Step | Result |
|---|---|
| The token | RS256, 1,534 bytes, 5 minutes; `aud` `["aries.example.com", "account"]`, `azp` `ci-example`; the made-up claims present; no ID token offered |
| The same verifier as people's, with audience `aries.example.com` and no nonce | Verified |
| A rule pinning `repository_id` and `ref` for `ci-example`, beside one for another repository | Matched; `ci-example` gets a key for an hour, `expiry-time` an hour ahead, `Z` |
| A rule pinning only `sub` | Refused when made: `pins only sub` |
| The same token at the people's verifier (audience `aries-cli`) | Refused: wrong audience. A workload token is not a person's sign-in |
| Only the other repository's rule | Refused: no rule matches |

Keycloak's access token carried `account` as a second audience, which the people's rule for several audiences (`azp` must be ours) would have refused; workload tokens are therefore checked without it (`oidc.Config.IDToken` false). What a real platform's token carries is for the real-tenant spikes (section 7).

## 4. sshd and expiry-time

`spike sshkeys` wrote a keys file of seven lines, each with its own key and `expiry-time` in one of three forms, three minutes ahead or one minute behind; `spike probe` connected with each key alone; a line from `spike login` was added in the UTC runs. The container's zone was set by `/etc/localtime` and `TZ` before sshd started. Its clock was the Mac's.

| Line's value | UTC | Pacific/Kiritimati (UTC+14) | Pacific/Pago_Pago (UTC−11) |
|---|---|---|---|
| UTC digits with `Z`, 3 min ahead | admitted | admitted | admitted |
| UTC digits with `Z`, 1 min behind | refused | refused | refused |
| UTC digits, no `Z`, 3 min ahead | admitted | **refused** | admitted |
| UTC digits, no `Z`, 1 min behind | refused | refused | **admitted** |
| The zone's own digits, no `Z`, 3 min ahead | admitted | admitted | admitted |
| The zone's own digits, no `Z`, 1 min behind | refused | refused | refused |
| The line `spike login` returned (UTC, `Z`, a day ahead) | admitted, its forced command run with `--principal alice --key SHA256:…` | | |

Identical on OpenSSH 9.6p1 and 10.2p1, in every run, every case as predicted from the rule below.

- **The answer to decision 54's zone question:** sshd reads fourteen digits with no `Z` in the server's zone, and digits ending in `Z` as UTC, as `sshd(8)` says. On a server west of UTC, a line written in UTC without `Z` admits a key that ended up to the zone's offset ago: here a key a minute expired was admitted, with eleven hours left. East of UTC, it ends a key early. **ariesd writes UTC with `Z`, always**; both versions the guide supports accept it.
- **An open connection outlives its line.** A connection made 59 seconds before its line's end was still receiving its forced command's output 15 seconds after it, on both versions; a new connection with the same key was then refused. sshd checks once, at authentication, so the daemon must close connections at the end (decision 59).
- **sshd's log.** At the guide's `LogLevel VERBOSE`, a line refused for its time is logged as `Refused by key options` (9.6p1), and with the file and line number on 10.2p1 (`… at /var/lib/aries/.ssh/aries_keys:3`). Neither says it was the time.

## 5. The dependency question

The token check needs RS256 and ES256 over keys from a JSON Web Key Set, and a dozen claim checks. The standard library does all of it: `crypto/rsa.VerifyPKCS1v15`, `crypto/ecdsa.Verify` over the 64-byte R‖S form, `ecdsa.ParseUncompressedPublicKey` (Go 1.25 and later) for an EC JWK, `encoding/base64.RawURLEncoding.Strict()`, `encoding/json`. `jose/jose.go` is 200 lines with its comments, refuses `none`, the HMAC family, `crit`, padded base64, RSA under 2,048 bits, curves other than P-256, a key whose type disagrees with the header's algorithm, and encryption keys, and has a fuzz target that ran 12 million inputs for 20 seconds with no finding. The verifier around it (`oidc/`) is 282 lines.

The alternative is `github.com/go-jose/go-jose/v4` (Apache-2.0, the library `coreos/go-oidc` uses), which brings the whole of JOSE, encryption included, to verify two algorithms. **Recommended: no new dependency.** The build moves `jose/` and `oidc/` into `internal/`, with their tests and the fuzz target, where rule 4 asks for exactly this. What a library would add that this lacks is breadth Aries should refuse anyway; what it would remove is about 200 lines to review.

## 6. What each provider will differ in

What the code takes per provider is settings: the issuer, the client id, the subject claim and claims that must equal a value. What will differ, from documentation (access-research §5, read 13 Oct 2026) and to be checked in section 7:

| | Google Workspace | Microsoft Entra ID | Okta | GitHub |
|---|---|---|---|---|
| Subject to store | `sub` | `oid`, with `tid` in the issuer (`sub` differs per app) | `sub` | Numeric user id, from `GET /user` |
| Must equal | `hd` | `tid` | (the issuer is the company's) | Organization membership, from the API |
| Code exchange | Needs the desktop client's secret, held by the server | Public client, no secret | Native app, PKCE, no secret | The App's client secret, held by the server; PKCE to be checked |
| Forced re-authentication | No `prompt=login`; `max_age` to be checked | `prompt=login` | `prompt=login`, `max_age` | None |
| Device grant | A separate "TVs and limited input" client, with a secret | "Allow public client flows"; often blocked by Conditional Access | A grant on the app | A switch on the App |
| Signing | RS256 | RS256 | RS256 | No ID token |

For workloads: GitHub Actions (`token.actions.githubusercontent.com`, audience chosen per request, claims `repository_id`, `repository_owner_id`, `ref`, `environment`, `job_workflow_ref`), Google Cloud (`accounts.google.com`, `sub` is the service account's unique id, audience chosen per request), Azure (`login.microsoftonline.com/TENANT/v2.0`, `tid` and `oid`, the audience fixed by an app registration that stands for the server).

## 7. The real-tenant spikes: what the maintainer registers

Each registration is the maintainer's, in the maintainer's own tenant or organization. What the maintainer passes the agent who runs a spike is **public identifiers only**: issuer URLs, client ids, tenant ids, an organization's name, a repository's numeric id. **No secret is ever passed in a message, a transcript, a command line or a file in the repository.** Where a provider needs one (Google's desktop client secret, GitHub's App client secret), the maintainer writes it into a 0600 file outside the repository, on the machine where the spike runs, and gives the agent only its path; the spike reads it as `readSecret` does and never prints it. Delete each registration's secret after the spike, and the registration when it is no longer needed. Every redirect below is to loopback; nothing needs a public URL.

### Google Workspace

1. In a Google Cloud project of the Workspace: **APIs and services → OAuth consent screen**, audience **Internal** (only the Workspace's people), app name "Aries (spike)", scopes `openid`, `email`, `profile`, nothing else.
2. **Credentials → Create OAuth client ID**, type **Desktop app**. A desktop client takes a loopback redirect on any port with nothing registered (to confirm); no redirect URI is entered.
3. For the device grant's question only, a second client of type **TVs and Limited Input devices**.
4. Pass: the client id(s) and the Workspace's domain (`hd`). The desktop client's secret goes in a 0600 file; Google says such a secret is not treated as confidential, and it is handled as one anyway.
5. To learn: the nonce and `auth_time` in the ID token; whether `max_age=0` (or a small value) forces the sign-in page with an open session; whether the device grant returns a nonce; the ID token's lifetime.

### Microsoft Entra ID

1. **App registrations → New registration**, "Aries (spike)", **single tenant**. Platform **Mobile and desktop applications**, redirect URI `http://localhost` (Entra admits any port on localhost for this platform, to confirm; add `http://127.0.0.1` too if the portal allows) and `https://login.microsoftonline.com/common/oauth2/nativeclient` for the code-page variant.
2. **Authentication → Allow public client flows: Yes**, only for the device grant's question; leave it off otherwise.
3. **Token configuration**: no optional claims; under **Manifest**, check `removeUnverifiedEmailClaim` (or the current equivalent) and note what `xms_edov` says.
4. **API permissions**: `openid`, `email`, `profile` (Microsoft Graph, delegated); admin consent for the tenant.
5. **The device-code policy question:** in **Conditional Access → Policies**, note whether a Microsoft-managed policy blocking device code flow exists or is in report-only mode in this tenant, and whether the tenant is new enough to have it by default. Change nothing to answer it; report what is there.
6. For workloads, a second registration standing for the Aries server: **Expose an API**, Application ID URI `api://aries.example.com` (or the tenant's verified domain), no scopes needed for app tokens; set `accessTokenAcceptedVersion` to 2 in its manifest.
7. Pass: the tenant id, both client ids and the Application ID URI. No secret: the people's client is public.

### GitHub

1. **A GitHub App** in the maintainer's organization (Settings → Developer settings → GitHub Apps → New): name "Aries spike (example)", homepage any URL, **Callback URL** `http://127.0.0.1/callback` (to learn whether any port is admitted), **Expire user authorization tokens** on, **Request user authorization (OAuth) during installation** off, **Enable Device Flow** on for the device question, **Webhook** inactive. **Permissions: none at all**, repository, organization and account; the user token's identity is all that is needed, and `GET /user/memberships/orgs/ORG` for the organization the App is installed on (to confirm that no permission is needed for it). Install it on the organization, all repositories off.
2. Generate a **client secret** and put it in a 0600 file; no private key for the App is needed (the App never acts as itself).
3. Pass: the App's client id, the organization's login.
4. To learn: whether the code exchange accepts PKCE, and works without the secret; the loopback port rule; that membership is visible; that `DELETE /applications/{client_id}/token` revokes the user token.

**An Actions workflow that prints the token's claims and not the token**, in a throwaway repository of the organization:

```yaml
name: oidc-claims
on: workflow_dispatch
permissions:
  id-token: write
  contents: read
jobs:
  claims:
    runs-on: ubuntu-latest
    steps:
      - name: Print the OIDC token's claims, never the token
        run: |
          set -eu
          tok=$(curl -fsS -H "Authorization: Bearer $ACTIONS_ID_TOKEN_REQUEST_TOKEN" \
            "$ACTIONS_ID_TOKEN_REQUEST_URL&audience=aries.example.com/n/test-nonce" | jq -r .value)
          echo "::add-mask::$tok"
          printf '%s' "$tok" | cut -d. -f1 | tr '_-' '/+' | base64 -d 2>/dev/null | jq -c '{alg, kid, typ}' || true
          printf '%s' "$tok" | cut -d. -f2 | tr '_-' '/+' | awk '{ n = length($0) % 4; if (n) $0 = $0 substr("===", n); print }' | base64 -d | jq 'del(.jti)'
```

It masks the token, prints only the header's algorithm and key id and the payload's claims, and needs no secret. Run it by hand on `main` and on a branch, and once from a pull request of a fork if the organization allows, to see what `ref`, `event_name` and `sub` say and whether a fork gets a token at all. Pass the output.

### Google Cloud: a service account's ID token

1. In a project: **IAM → Service accounts → Create**, `aries-spike@PROJECT.iam.gserviceaccount.com`, **no roles**.
2. Get an ID token for it with the audience chosen, without a key file: either from a Compute Engine VM or Cloud Run job that runs as it (`curl -H 'Metadata-Flavor: Google' 'http://metadata.google.internal/computeMetadata/v1/instance/service-accounts/default/identity?audience=aries.example.com/n/test-nonce&format=full'`), or by impersonation from the maintainer's own account with `roles/iam.serviceAccountOpenIdTokenCreator` on that account: `gcloud auth print-identity-token --impersonate-service-account=aries-spike@PROJECT.iam.gserviceaccount.com --audiences=aries.example.com/n/test-nonce --include-email`.
3. Decode and pass the claims only, as the workflow above does; never the token. Pass the service account's numeric unique id and email.

### Azure: a managed identity or a service principal

1. Prefer a **user-assigned managed identity** (`aries-spike`), attached to a small VM or a container app, with **no role assignments**. From inside it: `curl -H Metadata:true 'http://169.254.169.254/metadata/identity/oauth2/token?api-version=2018-02-01&resource=api://aries.example.com'`, with the Application ID URI of the server's registration (Entra, step 6).
2. Or a **service principal with a federated credential** (the GitHub Actions workflow above as the subject), which needs no secret: the job exchanges its GitHub token for an Entra token for `api://aries.example.com/.default`. A service principal with a client secret is the case to avoid, and need not be tested.
3. Decode and pass the claims only: `iss`, `aud`, `tid`, `oid`, `azp` or `appid`, `ver`, the lifetime. Pass the tenant id and the identity's object id.

## 8. What remains for the real-tenant spikes

- For each provider: the nonce and `auth_time` in the ID token; the loopback redirect's port rule; whether `prompt=login` or `max_age` forces a visible sign-in with a session open; the ID token's lifetime and signing algorithm.
- Google's and Entra's device grants: does a nonce come back, as with Keycloak? Does Entra's managed policy already block the grant in the maintainer's tenant?
- GitHub's App: PKCE, the secret, the port rule, membership, revocation.
- Server-side code exchange with each (the spike exchanged on the client).
- Workloads: whether GitHub Actions and Google Cloud accept an audience of the form `aries.example.com/n/NONCE`, so that a workload token binds to its key; what each token's claims are; Azure's token version and audience.
- None of this tests ariesd: the way in (identity.md §5) under AppArmor and systemd, and the daemon's close at expiry, are N0's and N2's.

## 9. Not tested here

- ariesd and `aries` themselves: a script stood in for the forced command, and `cmd/spike/server.go` for the daemon.
- The way in before sign-in (the published enrollment key, or the key command); access-research §3 measured its sshd side.
- Keycloak's `prompt=login` and `max_age` against a person who has also a second factor; the stand-in browser knows passwords only.
- `expiry-time` with thousands of lines, a clock that is wrong, or a clock set back while a connection is open.
- HTTPS to the provider: Keycloak ran on `http://127.0.0.1`, which the verifier admits for loopback only.
