# Aries v0.6.0

Decisions are named beside the items they settle
([design §14](../design/aries.md#14-decisions)).

## Summary

v0.6.0 is the minor release after v0.5.0 (decision 93), and the first
that upgrades in place: `ariesd upgrade` and `aries upgrade` take a
v0.5.0 install to it, with no new database, schema migration, key or
name. It speaks protocol 9 and still accepts 8, so v0.5.0's `aries`
keeps working against a v0.6.0 server.

What it adds: the HTTPS key proof bound to the TLS session where
`ariesd` terminates TLS, the deferred finding K-2 of v0.5.0's security
review; acceptance items settled at `handoff`, so that an agent's work
closes when it lands; cost per outcome in `aries cost`; the reasons an
issue is held by a gate, in `blocked`, `show` and at the write that
held it; `aries watch --events`; and Sextant's first slice, X0, an
exporter of each project's cost, built from source and not yet
released (decision 100). And fixes: `ariesd`'s HTTPS listener stops at
once with a request held, a signed-in client that stops reading is
closed, a race between a WebSocket's key proof and its close is gone,
and `recall` by key returns a memory whole.

## Read first

- **The protocol is 9, and v0.5.0's clients keep working.** `aries`
  v0.6.0 speaks protocol 9; `ariesd` v0.6.0 accepts 8 and 9, so
  v0.5.0's `aries` keeps working against it (rule 10, decision 93).
  Protocol 9 is this release's one bump, and carries three changes:
  `handoff` takes `ticked` and `waived`, so that an agent settles its
  acceptance items at handoff; the HTTPS key proof is bound to the
  TLS session ([Security changes](#security-changes)); and `cost`
  takes the grouping `outcome`.
  `aries` v0.6.0 against a v0.5.0 server is refused with code `version`
  (exit code 3) and told to have the server upgraded.
- **Upgrade `ariesd` first, then `aries`.** `ariesd upgrade` on the
  server, then `aries upgrade` on each machine, in that order. Nothing
  else is needed: no schema migration, no change to a config file, and
  the release key is v0.5.0's.
- **Behind a proxy, run ariesd with `tls: proxy`.** Over HTTPS, a key
  proof is now bound to the TLS session where ariesd terminates TLS
  ([Security changes](#security-changes)). A proxy that terminates TLS
  and opens a TLS session of its own to an ariesd with `tls: files` is,
  to ariesd, a second session, and `aries` v0.6.0's key proofs are
  refused there; the documented setup, `tls: proxy`
  ([docs/server.md, Behind a proxy](../server.md#behind-a-proxy)), is
  unchanged. A sign-in's token is not affected.
- **`cache_write` in `aries.usage.tokens` is now the five-minute cache
  write alone** ([Metrics](#metrics)). A query or an alert that sums
  `cache_write` for every cache write adds `cache_write_1h`.

## What's new

### Acceptance items settled at handoff

- **`handoff` with state `done` takes `ticked` and `waived`** (the MCP
  tool and the protocol), applied in the handoff's own write. Under a
  project's workflow an agent cannot `finish` before its work lands, so
  it hands off with its met items ticked and the others waived with a
  reason, and the closing pass of `landed` then closes the issue with
  nothing left open. Ticks with any other state, or on a closed issue,
  are refused `invalid`; a late handoff kept as a comment ticks
  nothing. The `acceptance` refusal of `finish` now tells an agent to
  hand off with `ticked` ([Agents](../agents.md),
  [The workflow](../concepts.md#the-workflow)).

### Why an issue is not ready

- **Gates that hold an issue are named.** An issue under an epic whose
  approval gate has not passed, or behind any open gate, is left out
  of `ready`, and now says why: the MCP `blocked` tool gives `gates`,
  one line for each open gate among the blockers, who passes it and the
  person's command `aries gate pass ID`; `show` gives `held`, the same
  lines for the gates that hold the issue through a parent or a
  blocker; and `create`, and `update` when it sets a parent, return
  `held`, which `aries create` prints on stderr
  ([Gates](../concepts.md#gates)). New result fields only.

### Cost per outcome

- **`aries cost --group-by outcome`** groups the window's usage by how
  each issue stood at the window's end: `landed` (its last close was
  by the check `landed`), `closed` (any other close), `open` and
  `(unattributed)`. Each group gives the issues counted and the rework,
  usage after an issue's first close. `landed` adds the cost per landed
  issue, by issue type, and the dearest landed issues (`-n`), each with
  its time held over its cycle time and the items and gates waived.
  Computed when read, at the prices of the time of reading; nothing is
  stored and no instrument is added
  ([Cost per outcome](../concepts.md#cost-per-outcome)).

### Watching every event

- **`aries watch --events`** prints every event committed on an issue,
  the watcher's own included, as `{"op":"event","event":{…}}` beside
  the inbox items (a line of text without `--json`), and keeps the
  events on after a `resync`. For a program that follows a project,
  such as the dispatcher of decision 96. It needs no newer server
  ([aries watch](../cli.md)).

### Memories

- **`recall` with `key` returns a memory's whole body,** up to the
  store's 4,096-byte cap, where it cut every body to 1,000 bytes; a
  body that JSON escaping swells past the result budget is still cut,
  and says so. Searches without `key` cut as before. An agent that
  edits a memory with `remember` and `rev`, which replaces the whole
  body, reads it by key first ([Agents](../agents.md)).

### Sextant X0 (decisions 98 and 100)

- **`sextant`**, a binary of its own that runs beside one `ariesd`,
  reads each project it is given through the ops `aries` already
  sends (`prices`, then `cost` by model), and exports each project's
  list-price cost over the window as `sextant.cost.usd` (by `project`
  and `model`), and its own failures as `sextant.scrape.errors`, over
  OTLP/HTTP from the `OTEL_*` variables and on a Prometheus endpoint
  on loopback, with `/healthz` and `/readyz`. It signs in with a key of
  its own, or as a service principal with its platform's token, and
  reads as a member with no admin right. A failed poll clears the
  project's figures rather than leave them stale. A model is a label
  only if the server's price table has it, as for
  `aries.usage.tokens` (decision 92). `sextant.yaml` has limits of its
  own ([Running Sextant](../sextant.md)).
- **Built from source only.** Sextant has no release asset, installer
  line, systemd unit or AppArmor profile in v0.6.0: those are slice X5.
  Build it from a checkout at the tag, as the guide says. It needs no
  protocol change and works against a v0.5.0 server. `aries` links none
  of it, and it links nothing `ariesd` does not (`internal/depcheck`).
  Cost by account, tokens and hours (X1), flow (X2) and a dashboard
  with alert rules (X3) are not built
  ([sextant.md §5](../design/sextant.md#5-slices)).

### For CI and contributors

- **The `deps` check** (`.github/workflows/deps.yml`), a job of its own
  on each pull request: the dependency policy of `deps.allow`, and a
  cooldown, by which a module version a pull request takes was
  published at least 14 days before, 30 for a new major version, unless
  the pull request is labeled `security-fix`. Every workflow job must
  have a `timeout-minutes` ([The deps check](../ci.md#the-deps-check)).
- **The `Aries:` trailer check** (`.github/workflows/trailer.yml`)
  fails a pull request whose commits name no issue, or name two, since
  `aries land` finds a squash merge's issue by its trailer alone; the
  label `no-issue` exempts one
  ([The `Aries:` trailer](../../CONTRIBUTING.md#the-aries-trailer),
  [How a job finds its issue](../ci.md#how-a-job-finds-its-issue)).
- **`scripts/gate.sh --pgtest-lock`** (or `ARIES_GATE_PGTEST_LOCK=1`)
  runs each whole-suite `go test` under the Aries lock `pgtest/HOST`,
  two at a time, so that agents testing in parallel on one machine do
  not run out of System V shared memory
  ([Agents testing in parallel on one machine](../../CONTRIBUTING.md#agents-testing-in-parallel-on-one-machine)).
  `internal/pgtest` now says when a server could not start for want of
  System V shared memory or semaphores, with the end of its log.
- **A credential store** for Aries's own secrets, `internal/credential`
  (decision 96): the macOS keychain, the Secret Service or else a 0600
  file on Linux, with the secret on stdin alone and never in an
  argument; Windows refuses until it is needed. No command uses it in
  v0.6.0; the dispatcher will be its first caller.

## Metrics

- **`aries.usage.tokens` counts the one-hour cache write apart.** The
  `kind` value `cache_write_1h` is new, and `cache_write` is now the
  five-minute part alone; it used to include the one-hour part. The
  server dashboard's token panels show tokens by model and kind.
- No name ariesd reports was renamed or removed
  ([Names that are kept](../server.md#names-that-are-kept)).

## Fixes

- **A held request no longer slows ariesd's stop** (finding L-3 of the
  [v0.5.0 security review](../design/security-review-v1.md),
  aries-hguptcq2). A request whose headers or body never finished
  arriving held every stop, restart and `ariesd upgrade` for the
  listener's 5-second wait. Now, at the stop, every read of a request's
  headers or body is cut off at once, over HTTP/1.1 by its connection
  and over HTTP/2 by its stream, while a request already in is still
  answered.
- **A race between a WebSocket's key proof and its close.** The bound
  on a connection's messages was changed during the key proof and read
  by a close from another goroutine, which `-race` caught in the HTTPS
  soak when ariesd restarted mid-proof (aries-2cjs2bbp). Writes now
  have a bound of their own that never changes. Nothing a client sees
  changes.
- **A client that stops reading is closed** (finding W-2 of the
  security review, aries-gl5dhcr5). Once a WebSocket's key was proved,
  nothing bounded the server's writes to it, so a signed-in client that
  pinged and then read nothing held the server's pong, its pings and
  every push behind them, and its connection slot, until the kernel
  gave up. Each frame the server writes after the proof now has
  `ws_write_timeout` (30 seconds by default, a new `limits:` setting,
  [Limits](../server.md#limits)); a write that times out closes the
  connection and frees its slot.
- **`recall` by key** no longer cuts a memory's body
  ([Memories](#memories)).

## Breaking changes

- **`aries` v0.6.0 needs a v0.6.0 server.** Against a v0.5.0 `ariesd`
  it is refused at the handshake with code `version`, exit code 3, and
  a line saying to upgrade the server. A v0.5.0 `aries` keeps working
  against a v0.6.0 server.
- **`cache_write`** in `aries.usage.tokens` no longer includes the
  one-hour cache write, now `cache_write_1h` ([Metrics](#metrics)).
- **A proxy that re-encrypts to an ariesd with `tls: files`** has
  `aries` v0.6.0's key proofs refused, as a relay
  ([Read first](#read-first)); run ariesd with `tls: proxy` behind it.

## Security changes

- **The key proof is bound to the TLS session where ariesd terminates
  TLS** (finding K-2 of the [v0.5.0 security review](../design/security-review-v1.md),
  aries-tl2cc2df). With `tls: files` or `tls: acme`, the challenge asks
  for RFC 9266's `tls-exporter`, and `aries` signs its own TLS session's
  binding into the proof, so that whoever holds a certificate the
  client trusts for the server's name (one issued in error, a leaked CA
  of `server.ca`, a proxy that inspects TLS) can no longer relay a
  proof to ariesd and act as its principal. Such a relay is refused
  with `the key proof does not verify for this TLS session` and a fix
  that names TLS inspection. `aries` v0.6.0 never signs the unbound
  proof of v0.5.0, so stripping the binding from the challenge gains a
  relay nothing.
- **Not covered, until `ProtoMin` moves to 9:** v0.5.0's `aries`
  (protocol 8) signs a proof that binds nothing, and v0.6.0's `ariesd`
  still takes it, so that those clients keep working: a relay can still
  take theirs. This window stays open until a release raises
  `ProtoMin` to 9. An operator whose clients are all v0.6.0 or later
  closes it now with the new setting `https: refuse_key_proof_v1: true`
  ([docs/server.md, Settings](../server.md#settings)), off by default;
  a v0.5.0 client it refuses is told to run `aries upgrade`.
- **Not covered: behind a proxy** (`tls: proxy`), ariesd never sees the
  client's TLS session, and nothing is bound; the proxy's certificate
  stays the only defense, as
  [security-model.md](../security-model.md#the-https-listener) says.
- **A held request cannot slow every stop, and a client that stops
  reading cannot hold its connection** (findings L-3 and W-2, under
  [Fixes](#fixes)).
- **The credential store** keeps a secret out of every argument, log
  and error: it refuses to start a command whose arguments carry the
  secret, redacts it from what an error quotes, and refuses a file
  store that is not the user's own at mode 0600. No command uses it
  yet.
- **The supply chain:** the `deps` check holds every module version a
  pull request takes to the cooldown of
  [supply-chain.md](../design/supply-chain.md#73-the-update-and-cooldown-policy) §7.3, and every workflow
  job to a timeout.

## Supported platforms

| Part | Platforms |
|---|---|
| `aries` | Linux, macOS and Windows, on amd64 and arm64. The outbox and the cache have not run on Windows |
| `ariesd` | Linux, on amd64 and arm64. Supported: Ubuntu 24.04 LTS and 26.04 LTS. Systems that run SELinux are not supported yet |
| `sextant` | Built from source, for Linux, macOS and Windows; meant to run on the server's machine. No release asset in v0.6.0 (X5) |
| Database | Postgres 16 or newer, on the machine or another, or a managed service. The tests pin Postgres 18.6 (`version.Postgres`), unchanged since v0.5.0; the installer installs 18 from the PostgreSQL project's apt repository (decision 81) |
| Agents | Claude Code, Codex, Gemini CLI, Cursor, VS Code, Junie, JetBrains AI Assistant and Claude Desktop, through `aries setup`; a remote MCP endpoint comes in 1.x (decision 90) |
| Identity providers | None promised: keys only (decision 91). Sign-in through an OpenID Connect provider and service principals stay as in v0.5.0, off unless configured and untested against a real provider |
| Transports | HTTPS by default; SSH when an operator turns it on (decision 86) |

## Not in this release

Moved out of v0.6.0 on 19 Oct 2026, to a later minor release; each
names its Aries issue:

- ACME against a real certificate authority, Let's Encrypt's staging
  and then production (aries-pk55wedb); ACME has still run only against
  a test CA ([Not verified](#not-verified)).
- A rate on new HTTPS connections and TLS handshakes from one address,
  finding L-5 of the security review (aries-bt467whn).
- The review's other minor findings: one client's refusals behind a
  proxy using up the refusal log's allowance, P-2 (aries-uxkbuv7r), and
  `client_secret_file` read once with the mode of what was opened
  checked, S-3 (aries-szcyh6ug).
- The work metrics beyond cost per outcome
  ([productivity-metrics.md](../design/productivity-metrics.md)).
- Recorded briefs, and the scheduled pull job that runs `aries land`
  (`aries setup pull-job`, aries-yryu7pv6).
- Lessons as a field on `handoff` and `finish` (L2, aries-l436tgkj),
  which is protocol 10's.
- Sextant's release (X5) and its slices X1 to X3.

## For contributors

- The `deps` and `Aries:` trailer checks run on every pull request
  ([For CI and contributors](#for-ci-and-contributors)); making either
  required is a ruleset setting.
- Tests that flaked on a busy machine were made reliable: the dead
  collector's port is held so that no other test takes it
  (`clienttest.DeadPort`), the silent collector's listener is closed
  before the goroutine-leak check (`clienttest.SilentPort`), the soak's
  refused mode holds its dead collector's port too, a test's
  port is retried when another process takes it, and `TestListen` waits
  for a closed socket to refuse connections.
- `deploy/docker/smoke.sh` runs in every mode (HTTPS, SSH, telemetry,
  identity and proxy) every night on `main`, and by hand
  (`.github/workflows/smoke.yml`), so that a mode two merges break
  between them shows within a day. It never runs on a pull request and
  is not a required check.

## Not verified

What this release has not run:

- the soaks over HTTPS and with telemetry checked, and the soaks on
  Linux or amd64: the release candidate ran the long and partition
  soaks over SSH on a Mac;
- what the installer's containers cannot cover: AppArmor, a real boot
  (sshd, ufw and journald as booted), time sync, a real network (DNS,
  a firewall, ports reached from outside), ACME, amd64, the real
  release key and the signatures and checksums of the real v0.6.0
  archives, and `ariesd upgrade` and `aries upgrade` themselves;
- the installer on a real machine, which the maintainer runs only after
  the tag (aries-g446t7vk): results to come;
- ACME against a real certificate authority, which has run only
  against a test CA (aries-pk55wedb);
- a rate limit on new HTTPS connections from one address, which ariesd
  does not have (aries-bt467whn); the nginx block the guide gives
  limits connections per address in front of it;
- the key proof's binding against a real TLS-inspecting product, or
  over a TLS session without the extended master secret, which Go's
  client always negotiates;
- Sextant outside the tests, and the credential store against a real
  Secret Service;
- what v0.5.0's notes list and v0.6.0 does not change: the outbox and
  the cache on Windows, a real network partition, a cloud provider's
  machine, a cold boot with the AppArmor profiles enforced, a managed
  Postgres and a standby's failover, and sign-in against any real
  provider ([v0.5.0, Not verified](v0.5.0.md#not-verified)).
