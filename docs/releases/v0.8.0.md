# Aries v0.8.0

Decisions are named beside the items they settle
([design §14](../design/aries.md#14-decisions)).

## Summary

v0.8.0 is the minor release after v0.7.0 (decision 93), and a small
one: eight pull requests (331 to 338). It upgrades in place, with one
schema migration (migration 4, which adds the `briefs` table), and it
speaks protocol 11 and accepts 10 and 11: `ProtoMin` moves to 10, so
v0.6.0's `aries` is no longer served.

What it adds: briefs stored on the issue they start, through a new
CLI-only op, `brief`, joined to the claim the started session takes
([design §22](../design/aries.md#22-briefs-stored-on-the-issue-they-start)).
And, with no change in behavior but one line: one rule for when an
issue may close, shared by close, finish and the closing pass; and a
test that holds every op to a rule for when the server cannot be
reached. The rest is documentation and this repository's own setup.

## Read first

- **The protocol is 11, and v0.6.0's clients stop working.** `aries`
  v0.8.0 speaks protocol 11; `ariesd` v0.8.0 accepts 10 and 11. v0.7.0's
  `aries` keeps working against a v0.8.0 server (rule 10, decision 93);
  v0.6.0's (protocol 9) is refused at the handshake with code `version`,
  exit code 3, and told to run `aries upgrade`. `aries` v0.8.0 against a
  v0.7.0 server is refused the same way, with a line saying to upgrade
  the server. Protocol 11 is this release's one bump: the op `brief`.
- **Upgrade `ariesd` first, then `aries`.** `ariesd upgrade` on the
  server, then `aries upgrade` on each machine, in that order. The
  server migrates each project's schema when it starts (migration 4,
  a new empty table); nothing else is needed: no change to a config
  file, and the release key is v0.5.0's. An older `ariesd` refuses a
  database this one migrated.

## What's new

### Briefs, stored on the issue they start

- **The op `brief`, CLI only** (aries-2qx4mlm2, PR 334; protocol 11).
  Whoever starts a session for an issue, a coordinator or `aries
  dispatch run`, records the brief it starts it with:
  `aries dispatch brief ID --record --model M --session S [--effort E]`
  renders the brief, records it and prints only the text to send;
  `--text TEXT` (or `-` for standard input) with `--template brief@N`
  records a text given instead. The dispatcher records each run's brief
  from its own session ([docs/agents.md, Briefs](../agents.md#briefs)).
- **What is recorded.** A comment of kind `brief`, whose first line is
  the `brief:` record (`harness`, `model`, `effort`, `session`,
  `template`), and beside it, in the `briefs` table, the fields, the
  brief's SHA-256, who recorded it from which session, and the claim it
  is joined to. A brief waits until the next `start` takes a new claim,
  which joins it in the same write (event `brief.bind`), or is joined at
  once to the live claim of the session it names; one brief per claim.
- **A session never briefs itself.** A brief from the session that
  holds the issue's live claim is refused, no MCP tool records one, and
  a sign-in of scope `mcp` or `ci` is refused the op. The text is held
  to safetext and the secrets lint, and capped by a new limit,
  `brief_bytes` (32,768 bytes by default, at most 64,000).
- **Who reads it.** `aries show` prints the latest brief's record and
  its claim (the text with `--full`), MCP `show` one line of its record,
  and `comments` and `history` the comment and its events. Everyone who
  may read the issue may read its brief.
- **Not built.** The merge rule's slice M4, which will read the stored
  brief, and only once workers run as a principal of their own role
  (decided 23 Oct 2026, [§22.4](../design/aries.md#224-what-the-merge-rule-may-trust)):
  until then `aries prs merges` reads the last `brief:` comment, and the
  opener stays unverified. `aries outcome` still reads the comment's
  line, and `ariesd export-bd` exports the comment, not the table.

### The brief template

- **Version 4 of `.aries/brief.txt`** (aries-nub37piw, PR 333) has a
  worker tick "CI green on the PR" once the required checks pass:
  version 3 said the landed check ticks it, which this repository's
  workflow does not bind, so an issue stayed open after it landed.

### Offline rules for every op

- **Every op has a rule for when the server cannot be reached**
  (aries-j2c6xary, PR 338; domain review R3). A test fails unless every
  write is queued or never queued with a reason, and every read is
  answered from the cache, refused, or not kept with a reason; it found
  46 ops with none, and each now has one from
  [design §18.3 to §18.6](../design/aries.md#183-the-outbox). The MCP tools take theirs
  from `internal/offline` rather than a list of their own. One line
  changes: `inbox` with `ack`, offline, now says the write was not
  queued and why, as every other unqueued write does.

### One close-readiness rule

- **`closeWaits`** (aries-ttlkklyw, PR 337; domain review R2) returns
  what keeps an issue from closing (holding gates, open items, required
  checks, open reviews), and close, finish and the closing pass all use
  it, where two copies could drift. No behavior changed; a person's
  close still releases a gate they may release, and the closing pass
  releases none.

## Fixes

- **An issue no longer stays open after it lands** because a worker
  left "CI green on the PR" for the landed check ([The brief
  template](#the-brief-template)).

## Breaking changes

- **`aries` v0.8.0 needs a v0.8.0 server.** Against a v0.7.0 `ariesd` it
  is refused at the handshake with code `version`, exit code 3, and a
  line saying to upgrade the server.
- **v0.6.0's `aries` is refused by a v0.8.0 server** (`ProtoMin` 10),
  with the fix `aries upgrade`.

## Security changes

- **A brief is never the worker's own** ([Briefs](#briefs-stored-on-the-issue-they-start)):
  the op is CLI only and refused from the session that holds the claim,
  so the recorder is someone other than the worker. Within one principal
  that is still the coordinator's word, not a proof; nothing in this
  release trusts a brief for a merge.
- **A brief is held to the secrets lint** and refused, naming the field
  and the kind, never the text, if it looks like it holds a credential.
- No change to the transports, sign-in, keys or the release key. The
  security review's finding L-5 stays for a later release.

## Removals

None.

## Supported platforms

| Part | Platforms |
|---|---|
| `aries` | Linux, macOS and Windows, on amd64 and arm64. The outbox and the cache have not run on Windows. `aries dispatch` runs on macOS and Linux |
| `ariesd` | Linux, on amd64 and arm64. Supported: Ubuntu 24.04 LTS and 26.04 LTS. Systems that run SELinux are not supported yet |
| `sextant` | Built from source, for Linux, macOS and Windows; meant to run on the server's machine. No release asset (X5) |
| Database | Postgres 16 or newer, on the machine or another, or a managed service. The tests pin Postgres 18.6 (`version.Postgres`), unchanged; the installer installs 18 from the PostgreSQL project's apt repository (decision 81) |
| Agents | Claude Code, Codex, Gemini CLI, Cursor, VS Code, Junie, JetBrains AI Assistant and Claude Desktop, through `aries setup`, unchanged from v0.7.0 |
| Identity providers | None promised: keys only (decision 91). Sign-in through an OpenID Connect provider and service principals stay as in v0.5.0, off unless configured |
| Transports | HTTPS by default; SSH when an operator turns it on (decision 86) |
| Go toolchain | 1.27.3 (building from source), unchanged |

## For contributors

- **This repository's Claude Code sessions run the guard** (PR 331):
  `.claude/settings.json` has the PreToolUse hook and the coarse copy
  of `.aries/guard.yaml`'s denies, as `aries setup claude-code --write`
  writes them. It needs an `aries` of v0.7.0 or later on `PATH`.
- **New design documents:** the [domain review](../design/domain-review.md),
  with a context map, a glossary and the leaks it found, and the
  maintainer's decisions on its ten questions (PR 335); and
  [packaging](../design/packaging.md), an icon and signed installers for
  macOS and Windows, nothing built (PR 332). PR 336 fixed the eight
  places the review found the docs disagreeing with the code.
- **`TestEveryOpHasAnOfflineRule`** (`internal/offline`) and
  **`TestCloseWaits`** (`internal/store`) are new: a new op needs an
  offline rule, and a new wait on closing goes in `closeWaits`.
