# Aries v1.0.0

> **Draft.** v1.0.0 is not released. These notes are kept current as its
> work lands. An item marked **(planned)** is not on `main` yet; the
> decision that puts it in the release is named beside it
> ([design §14](../design/aries.md#14-decisions)). When it merges, the
> pull request that lands it drops the mark. Nothing is tagged while an
> item is still marked: it either lands, or leaves these notes
> ([RELEASING.md](../../RELEASING.md#cutting-a-release)).

## Summary

v1.0.0 is the first release under the name Aries, and the first since
v0.4.0. It is a fresh start rather than an upgrade: a new name for
every binary, file, variable and path, a new release signing key, a new
license, and a new database, Postgres in place of Dolt **(planned,
decision 79)**. No v0.4.0 client or server carries over. Install
`aries` again, set up a new server, and follow
[Upgrading to 1.0](../upgrade-to-1.0.md).

What it adds since v0.4.0: many projects on one server, managed with
`aries admin`; observability for `ariesd`; work that goes on while the
server cannot be reached; human and CI gates, dates on issues, and
locks; and a server installer for Ubuntu LTS. **(planned, decisions
83, 85 to 87)** HTTPS becomes the primary transport, with SSH off
unless an operator turns it on; people sign in through their company's
identity provider (SSO), on the internet or with no route out at all;
service principals sign in with their platform's identity and hold no
stored key; and Claude's connectors and Claude Code can add Aries as a
remote MCP server by its URL.

## Read first

- **Reinstall `aries`; it cannot upgrade itself.** `aries upgrade` in
  v0.4.0 looks for releases under the project's former repository path
  and asset names, and trusts only the former release key. v1.0.0 has
  new asset names (`aries_…`, `ariesd_…`) and is signed by a new key, so
  a v0.4.0 client finds nothing it would install. Run the install script
  again ([Installing Aries](../install.md)).
- **Set up a new server.** No v0.4.0 server is moved: there is no
  migration from Dolt (decision 79). The guide's steps, or
  `install-server.sh`, set up a fresh one.
- **Every earlier client is refused.** A v1.0.0 server refuses every
  client of v0.4.x and earlier, and a v1.0.0 `aries` is refused by every
  earlier server, at the handshake, with exit code 3 and a line saying
  which side to upgrade. From v1.0.0 on, a release that changes the
  protocol keeps accepting the one before it (design principle 9).
- **SSH is off by default (planned, decision 86).** A new server
  serves HTTPS only. A team that reaches its server over SSH, IAP
  included, has the operator turn SSH on at installation
  (`install-server.sh --enable-ssh`, or `--profile ssh-only`).
- **Remove what the former install left.** The former binaries, the
  former project config file in each repository, the former agent setup
  and the former server files do nothing under the new names, and some
  of them (sshd's forced-command block, the sudo rule) still grant
  access. [Upgrading to 1.0](../upgrade-to-1.0.md#what-to-remove) lists
  them.

## What's new

### The name: Aries (decision 80)

The project is Aries: the module `github.com/ariesworx/aries`, the
client `aries` (with `aries mcp` for agents) and the daemon `ariesd`,
with no short alias. Everything else is named to match, with nothing
that reads another name:

- the repository config file, `.aries.yaml`;
- every client variable, `ARIES_*`, and every daemon variable,
  `ARIESD_*`;
- the commit trailer `Aries:`, which ties a commit to its issue;
- the MCP server's name, and the entries, pointer blocks
  (`<!-- aries:begin -->`) and hooks that `aries setup` writes;
- on the server: the `aries` account, the `ariesd.service` unit, the
  socket, `/etc/aries`, `/var/lib/aries`, `/opt/aries`, the keys file,
  the sudo rule, sshd's drop-in and the AppArmor profiles;
- the metrics, `aries.*` (`aries_*` in Prometheus), with the example
  alert rules, dashboard and Collector configuration to match;
- the release assets, `aries_<version>_<os>_<arch>` and
  `ariesd_<version>_linux_<arch>`;
- the operations plugin, `aries-ops`.

### Postgres (decision 79)

- A store interface in front of the store, so that the server's logic is
  tested apart from the database (slice P0). Merged.
- The store on Postgres, in place of Dolt (slice P1): Postgres's SQL,
  one migration set for a project and one for the control database,
  each starting again at `0001`, exact compare-and-swap on a row's
  revision, and each project a schema in one database. Postgres 16 or
  newer; the store's tests run in about a tenth of the time they took on
  Dolt. Dolt, its pin and its metrics are gone from the code. Merged.
- **(planned, decision 79, slice P2)** The daemon names and creates
  each project's schema itself, with one connection pool and a lock that
  keeps two daemons from writing one project. The status report reads the
  database's figures from Postgres's statistics.
- **(planned, decision 79, slice P4)** Operations on Postgres: the
  installer, the Docker test server, the AppArmor profiles, backups with
  `pg_dump`, upgrades, CI, and the guides. Postgres comes from the PGDG
  apt repository on servers (decision 81).
- **(planned, decision 79, slice P5)** The soak tests of stages 3, 3a and
  5 rerun on Postgres, on Linux.

On the spike's measurements, Postgres needs about a tenth of Dolt's
memory for each project and gives it back, answers the recursive reads
(ready, blocked) 2.7 to 3.9 times faster at 10,000 issues, and can be
run with a standby and failover by any cloud or with Patroni
(`spike/postgres/RESULTS.md`).

### HTTPS, the primary transport (decisions 86 and 87)

The designs are `docs/design/transport.md` and
`docs/design/identity.md` (decisions 85 and 87).

- **(planned, decision 86)** `ariesd` listens on HTTPS, and `aries` and
  `aries mcp` speak the same frames as before over one WebSocket.
  `.aries.yaml` gains `server.url`, and `server.ca` for a site's own
  certificate authority. TLS from the operator's files, from ACME, or
  ended at a proxy.
- **(planned, decision 86)** SSH is a second transport, off by default
  (`transports: [https]`), and turned on at installation or in the
  settings. It is kept for teams that sign in with keys alone, reach
  the server through IAP, or allow only SSH. `aries` against a server
  with SSH off is told to use the server's URL.
- **(planned, decision 87)** Installer profiles:
  `install-server.sh --profile internet` (the default), `private`,
  `airgapped` or `ssh-only`, and `--enable-ssh` to add SSH to any of the
  first three.
- **(planned, decision 86)** Air-gapped sites are first-class: HTTPS
  with the site's own CA, and sign-in through an identity provider
  inside the network (Keycloak, AD FS, Entra in a disconnected cloud),
  with its keys from an internal URL or a file. Nothing reaches outside
  unless configured to.

### Sign-in and tokens (decisions 83, 85 to 87)

- **(planned, decisions 83 and 86)** `aries login` signs a person in
  through the company's identity provider: OpenID Connect for Google
  Workspace, Microsoft Entra ID, Okta, Keycloak and AD FS, and GitHub
  through its own adapter (decision 87). In the browser where one is
  at hand, or by a URL that `aries login --url` prints, on any machine,
  where none is. `aries logout` ends the sign-in.
- **(planned, decision 87)** `ariesd` is its own authorization server: it
  exchanges the provider's code itself and issues a token of its own,
  opaque, stored only as a hash, and bound to a key on the person's
  machine (DPoP, RFC 9449), so that a copied token is useless. A
  sign-in lasts a day by default, 7 days at most, and is not renewed
  silently (decision 85).
- **(planned, decision 87)** Scopes: `cli` for a person's terminal,
  `mcp` for agents and connectors, `ci` for CI jobs. A token of scope
  `mcp` can never run an admin op or pass a gate.
- **(planned, decision 86)** Microsoft Entra ID in any cloud, its
  authority taken from configuration. The US Government clouds (GCC
  High, DoD) and the classified ones are configurable and not tested.
- **(planned, decision 85)** A person's identity: a handle, a display
  name, and the provider's identity of them, bound only to an
  invitation an admin made.
- **(planned, decision 87)** Over SSH, keys that expire:
  `aries admin key add --expires`.

### Service principals (decisions 83 and 87)

- **(planned, decision 87)** A CI job, an unattended agent or a cloud
  workload signs in as a service principal by exchanging its
  platform's token for an Aries token (OAuth 2.0 Token Exchange,
  RFC 8693): GitHub Actions' OIDC token, a Google Cloud service account,
  an Azure managed identity. `aries login --workload github-actions`
  (or `google`, `azure`). No stored key; a member's rights, scope `ci`.

### Claude: the remote MCP endpoint and the Desktop extension (decision 87)

- **(planned, decision 87)** A remote MCP endpoint,
  `https://aries.example.com/mcp/p/PROJECT`, that Claude's custom
  connectors (claude.ai, Claude Desktop, mobile) and Claude Code add by
  URL, with Aries's own sign-in. The same tools and budgets as
  `aries mcp`, one connector per project. A connector reaches the
  server from Anthropic's cloud, so it needs an internet-facing server;
  Claude Code on the person's machine works on a private network too.
- **(planned, decision 87)** A thinner Claude Desktop extension that
  carries `aries` for macOS and Windows and signs in by `aries login`'s
  flow, for private and air-gapped networks and for work that needs the
  machine, beside `aries setup claude-desktop`.

### Many projects on one server (stage 3a)

- One `ariesd` serves many projects, each with its own database and
  writer, with access by membership. Projects, principals, their keys
  and their memberships live in a control database.
- `aries admin` manages them from any machine: `admin project`,
  `admin principal`, `admin key`, `admin member`, and
  `admin status`, a report of the server and each project. Server admins
  and project admins.
- Keys reach sshd through a file `ariesd` writes from the control
  database, so adding a person needs no shell on the server.
- When a principal loses access, its connections are closed and its
  claims end.
- `ariesd control init` adopts an existing project and imports a
  hand-kept `authorized_keys`.

### Working without the server (stage 5)

- **The outbox.** A write `aries` or an agent makes while the server
  cannot be reached is kept on the machine and sent later, once, within
  7 days: `create`, `comment`, `handoff`, `remember`, logged hours,
  `finish`, `update`, labels, `dep add`, `accept` and token usage.
  `aries outbox` lists what waits and what was refused; `--no-queue` and
  `ARIES_NO_QUEUE` turn it off.
- **The cache.** With the server away, `prime`, `show`, `inbox` and
  `digest` answer from what the session last read, and say so; `ready`,
  `blocked`, `list` and `who` are refused rather than answered stale.
  `aries cache` manages it.
- **Conflicts.** An update replayed after others changed the issue is
  compared field by field; what conflicts is parked for a person to
  settle with `aries resolve`, and an agent may propose a resolution.
- **Late finishes.** A queued `finish` or `handoff` that arrives after
  its lease ran out applies if nobody took the issue since, and is kept
  as a comment if somebody did.
- **`aries away`** holds a person's claims through a planned absence,
  within the server's `away_max`.

### Gates, dates and locks (stage 6, slices G0 to G2)

- **Gates.** `aries gate add` holds issues until a person passes the
  gate; an agent may add one with the MCP `gate` tool, and only a person
  passes it, from their own terminal. `waive` and `rearm`.
- **CI gates.** A gate of kind `ci` waits for a check that a CI job
  reports with `aries gate pass` or `fail`, found by its branch.
  `landed`, reported after the merge, tells a closed issue from a landed
  one. Workflows for GitHub Actions and GitLab CI are in
  [CI gates](../ci.md).
- **Dates.** `--defer-until` and `--due` on `create` and `update` (and
  the MCP tools); `digest` and `prime` list what became ready, what is
  due soon and what is overdue.
- **Locks.** Leased, fenced, first-in-first-out mutexes and semaphores
  by name, held around a command with `aries lock run NAME -- CMD`, for
  a merge train, a deploy or a shared resource. Locks are for scripts,
  CI and people; agents do not take them.

Stage 6's G3 to G5 (graphs and formulas, swarm, cross-project
dependencies) come in 1.x releases as compatible additions (decision
81).

### Observability (stage 3b)

- Metrics and traces from `ariesd` over OTLP/HTTP, from the `OTEL_*`
  variables, with people named on a span by a stand-in, and a span that
  carries ids, codes and small numbers, never text.
- A loopback listener with `/metrics` for Prometheus, `/healthz` and
  `/readyz`; readiness and a watchdog for systemd; `ariesd status`.
- A log schema with stable event names, a request id on every line and
  in every refusal, an audit stream of access changes, and the same
  lines over OTLP as an option.
- Tested examples for operators in `deploy/observability`: a Collector
  configuration, alert rules and a dashboard.
- The database's figures in the status report: Dolt's today, and
  Postgres's **(planned, decision 79, slice P2)**.

### Running a server

- **`install-server.sh`** sets up a whole server, for many projects, on
  a fresh Ubuntu 24.04 LTS or 26.04 LTS machine, each step checking
  before it acts, with `--dry-run`
  ([With the installer](../server.md#with-the-installer)).
- **The `aries-ops` plugin** for Claude Code deploys and runs a server
  from an operator's workstation, showing every change before it runs
  ([Operate a server with Claude Code](../server.md#operate-a-server-with-claude-code)).
- **AppArmor profiles** for `ariesd`, optional.
- **The server's clock is checked, not trusted.** `ariesd` detects a
  clock that jumps or runs back, adds a forward jump to every live
  lease, and by default refuses to start with its clock behind its own
  history (`clock_behind`).
- **Release mirrors.** `install.sh`, `aries upgrade` and `ariesd upgrade`
  read releases from a static HTTPS host or a directory as well as from
  GitHub (`ARIES_RELEASES`, or `releases:` on a server), for servers with
  no way out. A mirror is never trusted: the signature decides.
- **Host key rotation.** `.aries.yaml` may pin a list of host keys
  (`host_keys`) while the server's key changes.
- **Connections.** A lighter bridge for each connection, 64 connections
  for each principal by default, and a deadline on every request.
- **A Docker test server** with smoke tests, and telemetry profiles
  that run a Collector and a Prometheus beside it.

### The client

- **Which key signs in.** With no key named, `aries` tries the default
  identity files of `~/.ssh` before ssh-agent's keys, as `ssh` does, and
  offers five at most. `ARIES_KEY_FILE` names one key file, and then
  only that key is offered. `aries whoami` shows which principal and
  which key a connection used.
- A faster start, and result budgets kept by search rather than one
  item at a time.

### Hardening (decisions 78 and 81)

- **(planned, decision 81)** A review of every public name, flag,
  variable and setting before they are fixed for 1.x. Names in these
  notes and in the upgrade guide may still change.
- **(planned, decision 78)** The protocol settled at one version, with
  the step-down code for versions no release spoke removed. The
  protocol's number stays out of routine output: it shows in `--json`,
  the status report's JSON and a refusal at the handshake.
- **(planned, decision 81)** The open follow-ups.

## Breaking changes

- **Every name changed** (above). Nothing reads a former name: not the
  former config file, not a former variable, not a former commit
  trailer, not a former MCP entry.
- **No in-place upgrade.** A v0.4.0 `aries` cannot upgrade itself, and
  a v0.4.0 `ariesd upgrade` cannot reach v1.0.0. Reinstall the client;
  set up a new server.
- **The protocol.** Every client and server of v0.4.x and earlier is
  refused (above).
- **The database.** **(planned, decision 79)** Postgres 16 or newer
  replaces Dolt. A v0.4.0 server's data is not migrated.
- **`key:` in `.aries.yaml`** may name only a file inside the
  repository. A line such as `key: ~/.ssh/id_ed25519` is refused, with
  its replacement: `ARIES_KEY_FILE=~/.ssh/id_ed25519`. A CI secret that
  held a private key for `aries` to read is never read: write the key to
  a file and set `ARIES_KEY_FILE` to its path
  ([Team deployment](../deploy/team.md)).
- **Key order.** The default identities of `~/.ssh` come before
  ssh-agent's keys, so a person with several registered keys may sign
  in with a different one than before.
- **The server's account** is `aries`, and `server.user` defaults to it.
- **The clock.** A server whose clock is behind its own history refuses
  to start unless told otherwise (`clock_behind`), and a usage record
  may be at most 5 minutes past the server's clock, not an hour.
- **Transport (planned, decision 86).** HTTPS is the default, and SSH is
  off on a new server until an operator turns it on
  (`install-server.sh --enable-ssh`, then `transports: [https, ssh]`).
  `aries` uses `server.url` when `.aries.yaml` has it, and SSH
  otherwise; `ARIES_TRANSPORT=ssh` chooses SSH where both are set.

## Security changes

- **A new release signing key.** v1.0.0 is signed by a new Ed25519 key,
  generated on 15 October 2026, which replaced the former key outright
  with no release that trusts both. Clients of v1.0.0 trust only the new
  key (`internal/release/keys.go`, and the PEM in `install.sh`). The
  former key signed v0.1.0 to v0.4.0; to verify one of those downloads
  by hand, check it out at its own tag
  ([Verify a download by hand](../install.md#verify-a-download-by-hand)).
- **The license** is the GNU Affero General Public License, version 3
  only (AGPL-3.0-only), copyright Ariesworx LLC, from 15 October 2026
  (decision 82). Releases up to v0.4.0 stay under Apache-2.0, as
  published. Contributions come under a contributor license agreement,
  [CLA.md](../../CLA.md) (decision 84), so that the code can also be
  offered under a commercial license.
- **Keys.** `key:` may no longer point outside the repository, and
  `ARIES_KEY_FILE` holds a path, never a key.
- **Access ends at once.** Removing a member, a key or a principal
  closes its connections and ends its claims.
- **The server refuses a globally trusted certificate authority** for
  its account, and the findings of the stage 3a security review are
  fixed.
- **No text in telemetry.** Spans and exported log records carry ids,
  codes and small numbers, never an issue's or a memory's text, a key, a
  token or an error's message.
- **The outbox and cache** are kept in a directory that must be the
  user's alone, and the secrets lint applies before anything is queued.
- **Releases from mirrors** are checked exactly as from GitHub; no
  redirect is followed.
- **(planned, decisions 86 and 87)** `ariesd` authenticates over HTTPS
  in its own code, where sshd did before: a security review of the
  listener and the authorization server comes before the release.
- **(planned, decision 87)** Tokens bound to the machine's key (DPoP),
  stored on the server only as hashes, revoked at once, with every
  connection they opened closed when they end; a token's scope decides
  what it may do, whatever the client sends.
- **(planned, decision 87)** Keys that expire over SSH, and service
  principals that hold no stored key.

## Removals

- **Dolt. (planned, decision 79)** The store, the installer, the
  Docker test server, the AppArmor profiles, CI and the guides lose
  Dolt, with: the Dolt pin and its checksums, `scripts/install-dolt.sh`,
  `internal/dolttest`, `internal/doltmetrics` and Dolt's figures in the
  status report, the tag taken before an upgrade, the commit loop, and
  the `write_id` column. The former migration sets are deleted.
- **The former names**, with no alias (decision 80).
- **The step-down code** for protocol versions no release spoke
  **(planned, decision 78)**.
- **`spike/dolt` and `spike/multidb`**, whose findings are summarized in
  `spike/postgres/RESULTS.md`.

## Supported platforms

| Part | Platforms |
|---|---|
| `aries` | Linux, macOS and Windows, on amd64 and arm64. The outbox and the cache have not run on Windows |
| `ariesd` | Linux, on amd64 and arm64. Supported: Ubuntu 24.04 LTS and 26.04 LTS. Systems that run SELinux are not supported yet |
| Database | **(planned, decision 81)** Postgres 16 or newer; the tests pin Postgres 18. Until the port lands, Dolt at the version in `internal/version` |
| Agents | Claude Code, Codex, Gemini CLI, Cursor, VS Code, Junie, JetBrains AI Assistant and Claude Desktop, through `aries setup`; **(planned, decision 87)** Claude's custom connectors and Claude Code through the remote MCP endpoint |
| Identity providers | **(planned, decisions 83, 86)** Google Workspace, Microsoft Entra ID (commercial cloud tested; US Government and classified clouds configurable, not tested), Okta, Keycloak, AD FS, and GitHub |
| Transports | **(planned, decision 86)** HTTPS by default; SSH when an operator turns it on |

## For contributors

- `main` takes squash merges through a merge queue, which runs `lint`
  and `test` on each pull request as it would merge.
- Contributions need a signed [CLA](../../CLA.md), through CLA
  Assistant Lite.
- Every test is parallel or says why not, and the gate fails a test run
  that leaves a file or a process behind.
