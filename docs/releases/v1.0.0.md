# Aries v1.0.0

> **Draft.** v1.0.0 is not released. These notes are kept current as its
> work lands. An item marked **(planned)** is not on `main` yet; the
> decision that puts it in the release is named beside it
> ([design §14](../design/aries.md#14-decisions)). When it merges, the
> pull request that lands it drops the mark. Nothing is tagged while an
> item is still marked: it either lands, or leaves these notes
> ([RELEASING.md](../../RELEASING.md#cutting-a-release)).

## Summary

v1.0.0 is the first release under the name Aries, and the first since
v0.4.0. It is a fresh start rather than an upgrade: a new name for
every binary, file, variable and path, a new release signing key, a new
license, and a new database, Postgres in place of Dolt (decision 79).
No v0.4.0 client or server carries over. Install
`aries` again, set up a new server, and follow
[Upgrading to 1.0](../upgrade-to-1.0.md).

What it adds since v0.4.0: many projects on one server, managed with
`aries admin`; observability for `ariesd`; work that goes on while the
server cannot be reached; human and CI gates, dates on issues, and
locks; a server installer for Ubuntu LTS; and HTTPS as the primary
transport, with SSH off unless an operator turns it on. **(planned,
decisions 83, 85 to 87)** People sign in through their company's
identity provider (SSO), on the internet or with no route out at all;
service principals sign in with their platform's identity and hold no
stored key; and Claude's connectors and Claude Code can add Aries as a
remote MCP server by its URL.

## Read first

- **Reinstall `aries`; it cannot upgrade itself.** `aries upgrade` in
  v0.4.0 looks for releases under the project's former repository path
  and asset names, and trusts only the former release key. v1.0.0 has
  new asset names (`aries_…`, `ariesd_…`) and is signed by a new key, so
  a v0.4.0 client finds nothing it would install. Run the install script
  again ([Installing Aries](../install.md)).
- **Set up a new server.** No v0.4.0 server is moved: there is no
  migration from Dolt (decision 79). The guide's steps, or
  `install-server.sh`, set up a fresh one.
- **Every earlier client is refused.** v1.0.0 speaks protocol 8 alone.
  A v1.0.0 server refuses every client of v0.4.x and earlier, and a
  v1.0.0 `aries` is refused by every earlier server, at the handshake,
  with exit code 3 and a line saying which side to upgrade. From
  v1.0.0 on, a release that changes the protocol keeps accepting the
  one before it (design principle 9).
- **SSH is off by default (decision 86).** A new server serves HTTPS
  only, and `ariesd serve` refuses to start with HTTPS on and no
  `https:` in its config. A team that reaches its server over SSH, IAP
  included, has the operator turn SSH on at installation
  (`install-server.sh --enable-ssh`, or `--profile ssh-only`), or sets
  `transports: [ssh]`.
- **Remove what the former install left.** The former binaries, the
  former project config file in each repository, the former agent setup
  and the former server files do nothing under the new names, and some
  of them (sshd's forced-command block, the sudo rule) still grant
  access. [Upgrading to 1.0](../upgrade-to-1.0.md#what-to-remove) lists
  them.

## What's new

### The name: Aries (decision 80)

The project is Aries: the module `github.com/ariesworx/aries`, the
client `aries` (with `aries mcp` for agents) and the daemon `ariesd`,
with no short alias. Everything else is named to match, with nothing
that reads another name:

- the repository config file, `.aries.yaml`;
- every client variable, `ARIES_*`, and every daemon variable,
  `ARIESD_*`;
- the commit trailer `Aries:`, which ties a commit to its issue;
- the MCP server's name, and the entries, pointer blocks
  (`<!-- aries:begin -->`) and hooks that `aries setup` writes;
- on the server: the `aries` account, the `ariesd.service` unit, the
  socket, `/etc/aries`, `/var/lib/aries`, `/opt/aries`, the keys file,
  the sudo rule, sshd's drop-in and the AppArmor profiles;
- the metrics, `aries.*` (`aries_*` in Prometheus), with the example
  alert rules, dashboard and Collector configuration to match;
- the release assets, `aries_<version>_<os>_<arch>` and
  `ariesd_<version>_linux_<arch>`;
- the operations plugin, `aries-ops`.

### Postgres (decision 79)

- A store interface in front of the store, so that the server's logic is
  tested apart from the database (slice P0). Merged.
- The store on Postgres, in place of Dolt (slice P1): Postgres's SQL,
  one migration set for a project and one for the control database,
  each starting again at `0001`, exact compare-and-swap on a row's
  revision, and each project a schema in one database. Postgres 16 or
  newer; the store's tests run in about a tenth of the time they took on
  Dolt. Dolt, its pin and its metrics are gone from the code. Merged.
- The daemon on Postgres (slice P2): `aries admin project add NAME`
  makes the project's schema itself, `project_NAME` (hyphens as
  underscores), and refuses a name whose schema is already in the
  database, so the operator sets aside no names (`project_dbs` is gone).
  One pool of connections serves every project, at most
  `db_conns_per_server` (32) with `db_conns_per_project` (8) for one
  project's reads, so a project nobody uses costs Postgres nothing. Each
  project's writer holds an advisory lock on its schema, as the daemon's
  control store does, so a second ariesd on the same database is refused
  a project, or the control store, that another serves, and
  `ariesd import-bd` asks for ariesd to be stopped first. The status
  report shows Postgres's own figures (connections, transactions,
  deadlocks, conflicts, temporary files, sizes) and each project's
  schema's size, read with ariesd's own role, and the pool is measured
  (`aries.db.pool.*`). `control_db` is `control_schema` now, with no
  alias. Merged.
- Operations on Postgres (slice P4). `install-server.sh` installs
  Postgres 18 from the PostgreSQL project's apt repository, with the
  repository's key checked against its pinned fingerprint as CI checks
  it; or uses a Postgres 16 or newer the machine already runs; or, with
  `--dsn` and `--db-password-file`, one on another machine or a managed
  service. It makes ariesd's role, which may log in and nothing more,
  and its database, owned by that role, with collation `C`; on the
  machine ariesd signs in by the unix socket with no password at all,
  and elsewhere the password is in a 0600 file the DSN names, never on a
  command line. The config file it writes has `control_schema` and no
  `project_dbs`. The Docker test server runs Docker's official
  `postgres:18` image, pinned by digest, beside the server's container.
  The AppArmor profiles reach Postgres's unix socket and read the
  database's client files in `/etc/aries/postgres`, and the daemon's
  allows DNS and the certificate authorities always, for a managed
  Postgres by name and over TLS. The server guide is Postgres's
  throughout: setup, settings, the role, the status report, sizing,
  managed services (Amazon RDS and Aurora, Google Cloud SQL and AlloyDB,
  Azure), standby and failover, upgrades, a daily `pg_dump` by a systemd
  timer, a restore of the whole database or of one project, and
  point-in-time recovery. The operations skill has the Postgres steps.
  Run: the installer on Ubuntu 24.04 and 26.04 in containers booted by
  systemd, with and without `--dsn`; the Docker smoke test, plain, with
  telemetry and with the identity provider; the backup and restore as
  the guide writes them. Not run: a virtual machine, so neither a real
  boot nor the AppArmor profiles enforced; a managed service. Merged.
- The soak tests of stages 3, 3a and 5 rerun on Postgres, on Linux
  (slice P5, its Linux part): 10 minutes of work each, under `-race`, on
  linux/amd64 in containers with Postgres 18 from the PostgreSQL
  project's repository, over SSH (176,557 requests) and over HTTPS
  (129,720), in partition mode (166,287, with 224 cuts and 8,303
  replays) and with telemetry checked against the event logs (183,473
  requests, 567,688 spans); every check passed. The installer ran again
  on Ubuntu 24.04 and 26.04 in containers booted by systemd, arm64, for
  the `private` profile with a test CA and for `ssh-only`: a dry run, a
  clean run, a rerun that changed nothing and a dry run that would
  change nothing, then `aries` from a Mac over HTTPS and over SSH. The
  peer check ran as root. `ariesd control init` no longer tells an
  installer with SSH off that sshd reads `/etc/aries/admin.keys`, which
  nothing reads. Still owed before the tag: the installer and the units
  under an enforcing AppArmor in a virtual machine, with a cold boot.

On the spike's measurements, Postgres needs about a tenth of Dolt's
memory for each project and gives it back, answers the recursive reads
(ready, blocked) 2.7 to 3.9 times faster at 10,000 issues, and can be
run with a standby and failover by any cloud or with Patroni
(`spike/postgres/RESULTS.md`).

### HTTPS, the primary transport (decisions 86 and 87)

The designs are `docs/design/transport.md` and
`docs/design/identity.md` (decisions 85 and 87).

- **(decision 86)** `ariesd` listens on HTTPS, and `aries` and `aries
  mcp` speak the same frames as before over one WebSocket
  (`internal/wsconn`, Aries's own, no dependency, decision 87), through
  proxies, which the server's pings every 25 seconds keep from closing
  an idle connection. `.aries.yaml` gains `server.url`, and `server.ca`
  for a site's own certificate authority. TLS from the operator's
  files, read again when they change, from ACME (`autocert`, Let's
  Encrypt or an internal ACME server), or ended at a proxy; TLS 1.2 or
  1.3, HTTP/2 for all but the WebSocket, and limits on connections,
  headers, bodies, messages and refused sign-ins
  ([Limits](../server.md#limits)). Until sign-in lands, a connection
  proves it holds one of the SSH keys the server knows, the same keys
  as over SSH, by signing a challenge and the server's URL; nothing is
  served without it ([How aries signs in over
  HTTPS](../server.md#how-aries-signs-in-over-https)).
- **(decision 86)** SSH is a second transport, off by default
  (`transports: [https]`), and turned on at installation or in the
  settings. It is kept for teams that sign in with keys alone, reach
  the server through IAP, or allow only SSH. With it off ariesd writes
  no keys file and refuses the bridge, naming the setting; `aries`
  against such a server is told to use the server's URL. The status
  report names the transports.
- **(decision 87)** Installer profiles:
  `install-server.sh --profile internet` (the default), `private`,
  `airgapped` or `ssh-only`, and `--enable-ssh` to add SSH to any of the
  first three; `--plan` says what a profile serves and writes.
  `--disable-ssh` turns SSH off again on a server that served it: it
  takes the `aries` account's `authorized_keys` into the control store,
  then removes it, sshd's drop-in, the keys file and the bridge's
  AppArmor profile, so that no SSH path is left
  ([SSH on and off](../server.md#ssh-on-and-off)).
- **(decisions 59, 87 and 89; slice S1)** Keys that end:
  `aries admin key add NAME FILE --expires 30d`, or `--expires` a time,
  for a contractor's key or a stopgap CI key, at most ten years away.
  A key past its end signs in over neither transport, on the server's
  clock: the keys file's line carries the end as sshd's `expiry-time`,
  in UTC marked `Z`, and goes at the end; the handshake and the proof
  over HTTPS refuse the key, saying when it ended; and the connections
  it signed in are closed at the end, by a timer, with a `key.expired`
  log line. `aries admin key list` shows each key's end, and an ended
  key is listed for an hour, then pruned
  ([Keys that end](../server.md#keys-that-end)).
- **(decision 86)** Air-gapped sites are first-class: HTTPS with the
  site's own CA, or an internal ACME server, and nothing reached
  outside. **(planned)** Sign-in through an identity provider inside
  the network (Keycloak, AD FS, Entra in a disconnected cloud), with its
  keys from an internal URL or a file.

### Sign-in and tokens (decisions 83, 85 to 87)

- **(planned, decisions 83 and 86)** `aries login` signs a person in
  through the company's identity provider: OpenID Connect for Google
  Workspace, Microsoft Entra ID, Okta, Keycloak and AD FS, and GitHub
  through its own adapter (decision 87). In the browser where one is
  at hand, or by a URL that `aries login --url` prints, on any machine,
  where none is. `aries logout` ends the sign-in.
- **(planned, decision 87)** `ariesd` is its own authorization server: it
  exchanges the provider's code itself and issues a token of its own,
  opaque, stored only as a hash, and bound to a key on the person's
  machine (DPoP, RFC 9449), so that a copied token is useless. A
  sign-in lasts a day by default, 7 days at most, and is not renewed
  silently (decision 85).
- **(planned, decision 87)** Scopes: `cli` for a person's terminal,
  `mcp` for agents and connectors, `ci` for CI jobs. A token of scope
  `mcp` can never run an admin op or pass a gate.
- **(planned, decision 86)** Microsoft Entra ID in any cloud, its
  authority taken from configuration. The US Government clouds (GCC
  High, DoD) and the classified ones are configurable and not tested.
- **(decisions 57, 60 and 85; slice N1)** A principal is a `person` or
  a `service`, with a display name, and a service answers to an owner,
  a person (`aries admin principal add --kind --owner --display-name`,
  `principal set`, `principal show`). A person's identities at the
  providers they sign in at are a table of their own, and the only way
  to one is an invitation: a server admin invites an address at a
  provider (`aries admin invite add NAME ADDRESS --provider P`, or
  `principal add --invite`), which lapses unused after 7 days
  (`login: invite_ttl`), and nobody invites one onto their own
  principal. `invite list` and `remove`, `identity list` and `remove`;
  caps `identities_per_principal` and `invites_per_server`; the audit
  stream's `audit.principal.set`, `audit.identity.invite` and
  `audit.identity.remove`, which never hold an address or a display
  name; and counts in `aries admin status`
  ([Identities and invitations](../server.md#identities-and-invitations)).
  **(planned, slice T2)** The sign-in that binds an invitation: until
  it lands, an identity is recorded and matches nothing.

### Service principals (decisions 83 and 87)

- **(planned, decision 87)** A CI job, an unattended agent or a cloud
  workload signs in as a service principal by exchanging its
  platform's token for an Aries token (OAuth 2.0 Token Exchange,
  RFC 8693): GitHub Actions' OIDC token, a Google Cloud service account,
  an Azure managed identity. `aries login --workload github-actions`
  (or `google`, `azure`). No stored key; a member's rights, scope `ci`.

### Claude: the remote MCP endpoint and the Desktop extension (decision 87)

- **(planned, decision 87)** A remote MCP endpoint,
  `https://aries.example.com/mcp/p/PROJECT`, that Claude's custom
  connectors (claude.ai, Claude Desktop, mobile) and Claude Code add by
  URL, with Aries's own sign-in. The same tools and budgets as
  `aries mcp`, one connector per project. A connector reaches the
  server from Anthropic's cloud, so it needs an internet-facing server;
  Claude Code on the person's machine works on a private network too.
- **(planned, decision 87)** A thinner Claude Desktop extension that
  carries `aries` for macOS and Windows and signs in by `aries login`'s
  flow, for private and air-gapped networks and for work that needs the
  machine, beside `aries setup claude-desktop`.

### Many projects on one server (stage 3a)

- One `ariesd` serves many projects, each with its own database and
  writer, with access by membership. Projects, principals, their keys
  and their memberships live in a control database.
- `aries admin` manages them from any machine: `admin project`,
  `admin principal`, `admin key`, `admin member`, and
  `admin status`, a report of the server and each project. Server admins
  and project admins.
- Keys reach sshd through a file `ariesd` writes from the control
  database, so adding a person needs no shell on the server.
- When a principal loses access, its connections are closed and its
  claims end.
- `ariesd control init` adopts an existing project and imports a
  hand-kept `authorized_keys`.

### Working without the server (stage 5)

- **The outbox.** A write `aries` or an agent makes while the server
  cannot be reached is kept on the machine and sent later, once, within
  7 days: `create`, `comment`, `handoff`, `remember`, logged hours,
  `finish`, `update`, labels, `dep add`, `accept` and token usage.
  `aries outbox` lists what waits and what was refused; `--no-queue` and
  `ARIES_NO_QUEUE` turn it off.
- **The cache.** With the server away, `prime`, `show`, `inbox` and
  `digest` answer from what the session last read, and say so; `ready`,
  `blocked`, `list` and `who` are refused rather than answered stale.
  `aries cache` manages it.
- **Conflicts.** An update replayed after others changed the issue is
  compared field by field; what conflicts is parked for a person to
  settle with `aries resolve`, and an agent may propose a resolution.
- **Late finishes.** A queued `finish` or `handoff` that arrives after
  its lease ran out applies if nobody took the issue since, and is kept
  as a comment if somebody did.
- **`aries away`** holds a person's claims through a planned absence,
  within the server's `away_max`.

### Gates, dates and locks (stage 6, slices G0 to G2)

- **Gates.** `aries gate add` holds issues until a person passes the
  gate; an agent may add one with the MCP `gate` tool, and only a person
  passes it, from their own terminal. `waive` and `rearm`. Those who
  pass it are told when it is added and when more work is put behind
  it: the approvers it names, or for a gate that names none, the
  project's admins.
- **CI gates.** A gate of kind `ci` waits for a check that a CI job
  reports with `aries gate pass` or `fail`, found by its branch.
  `landed`, reported after the merge, tells a closed issue from a landed
  one. Each report carries its run's number, so a slow run of an older
  commit cannot undo a newer run's result. Workflows for GitHub Actions
  and GitLab CI are in [CI gates](../ci.md).
- **Dates.** `--defer-until` and `--due` on `create` and `update` (and
  the MCP tools); `digest` and `prime` list what became ready, what is
  due soon and what is overdue.
- **Locks.** Leased, fenced, first-in-first-out mutexes and semaphores
  by name, held around a command with `aries lock run NAME -- CMD`, for
  a merge train, a deploy or a shared resource. Locks are for scripts,
  CI and people; agents do not take them.

Stage 6's G3 to G5 (graphs and formulas, swarm, cross-project
dependencies) come in 1.x releases as compatible additions (decision
81).

### Observability (stage 3b)

- Metrics and traces from `ariesd` over OTLP/HTTP, from the `OTEL_*`
  variables, with people named on a span by a stand-in, and a span that
  carries ids, codes and small numbers, never text.
- A loopback listener with `/metrics` for Prometheus, `/healthz` and
  `/readyz`; readiness and a watchdog for systemd; `ariesd status`.
- A log schema with stable event names, a request id on every line and
  in every refusal, an audit stream of access changes, and the same
  lines over OTLP as an option.
- Tested examples for operators in `deploy/observability`: a Collector
  configuration, alert rules and a dashboard.
- Postgres's own figures in the status report, and each project's
  schema's size; the daemon's pool of connections to it as metrics, with
  an alert and a panel for requests that wait for one.
- Gates as metrics and log events: `aries.gates` by kind and event, and
  the lines `gate.added`, `gate.passed`, `gate.failed`, `gate.waived` and
  `gate.rearmed`, with a panel on the dashboard.

### Running a server

- **`install-server.sh`** sets up a whole server, for many projects, on
  a fresh Ubuntu 24.04 LTS or 26.04 LTS machine, each step checking
  before it acts, with `--dry-run`
  ([With the installer](../server.md#with-the-installer)).
- **The `aries-ops` plugin** for Claude Code deploys and runs a server
  from an operator's workstation, showing every change before it runs
  ([Operate a server with Claude Code](../server.md#operate-a-server-with-claude-code)).
- **AppArmor profiles** for `ariesd`, optional. The bridge's,
  `ariesd-stdio`, is a file of its own, installed only with SSH on.
- **The server's clock is checked, not trusted.** `ariesd` detects a
  clock that jumps or runs back, adds a forward jump to every live
  lease, and by default refuses to start with its clock behind its own
  history (`clock_behind`).
- **Release mirrors.** `install.sh`, `aries upgrade` and `ariesd upgrade`
  read releases from a static HTTPS host or a directory as well as from
  GitHub (`ARIES_RELEASES`, or `releases:` on a server), for servers with
  no way out. A mirror is never trusted: the signature decides.
- **Host key rotation.** `.aries.yaml` may pin a list of host keys
  (`host_keys`) while the server's key changes.
- **Connections.** A lighter bridge for each connection, 64 connections
  for each principal by default, and a deadline on every request.
- **A Docker test server** with smoke tests, and telemetry profiles
  that run a Collector and a Prometheus beside it.

### The client

- **Which key signs in.** With no key named, `aries` tries the default
  identity files of `~/.ssh` before ssh-agent's keys, as `ssh` does, and
  offers five at most. `ARIES_KEY_FILE` names one key file, and then
  only that key is offered. `aries whoami` shows which principal and
  which key a connection used.
- A faster start, and result budgets kept by search rather than one
  item at a time.
- **`.aries.yaml` keys it does not know** are ignored, with one warning,
  rather than refused (decision 88), so that a key a later 1.x release
  reads does not stop an older `aries` that shares the file.

### Hardening (decisions 78 and 81)

- **A review of every public name, flag, variable and setting** before
  they are fixed for 1.x ([surface-review.md](../design/surface-review.md)),
  accepted whole (decision 88), and made: the default issue id prefix
  `ar`, the protocol settled with its names, one naming rule for
  `limits:`, and the rest listed under Breaking changes.
- **The protocol is settled at 8** (decisions 78 and 88), spoken alone:
  a client or server of any other version is refused at the handshake,
  and the code that stepped down to versions no release spoke is gone.
  The protocol's number stays out of routine output: it shows in
  `--json`, the status report's JSON and a refusal at the handshake.
  From v1.0.0 on, a release that changes the protocol keeps accepting
  the one before it.
- **The names ariesd reports are kept** within 1.x (decision 88): no
  metric, attribute value, span or log event or field is renamed or
  removed, and only additions are made
  ([Names that are kept](../server.md#names-that-are-kept)).
- **A restart of Postgres between requests logs nothing.** The pool
  hands out no connection that Postgres ended while it was idle, and
  makes another in its place.
- **(planned, decision 81)** The open follow-ups.

## Breaking changes

- **Every name changed** (above). Nothing reads a former name: not the
  former config file, not a former variable, not a former commit
  trailer, not a former MCP entry.
- **No in-place upgrade.** A v0.4.0 `aries` cannot upgrade itself, and
  a v0.4.0 `ariesd upgrade` cannot reach v1.0.0. Reinstall the client;
  set up a new server.
- **The protocol is 8, spoken alone** (decisions 78 and 88). Every
  client and server of v0.4.x and earlier is refused (above), and so is
  any build of 5 to 7, which no release spoke: with code `version`,
  exit code 3, and a fix saying which side to upgrade. A refused client
  says no second hello in another version, and what its outbox holds
  waits, unsent, for a server of 8. The welcome frame no longer carries
  `latest`.
- **The default issue id prefix is `ar`** (decision 88), where it was
  `sf`: a new project's ids start `ar-` unless `prefix:` (or
  `aries admin project add --prefix`, whose default is the project's
  name) says otherwise.
- **The protocol's names** (decision 88), which a script reading
  `--json` meets:
  - the op `resolve` is `conflict.resolve` (`aries resolve` is
    unchanged);
  - an issue's `parent_id` is `parent`, and its `due_at`, and a list's,
    is `due`;
  - a claim's and an overlap's `id` is `issue`, and so is the issue
    `hours.log` takes;
  - the principal in the results of `admin principal add`, `disable`
    and `enable` and of `admin member add` and `remove` is `name`, and
    the key in the results of `admin key add` and `remove` is
    `fingerprint`;
  - `lock release`'s `released` is `epoch`;
  - the inbox kinds `assigned`, `mention`, `handoff` and `conflict` are
    `issue.assigned`, `issue.mentioned`, `issue.handoff` and
    `conflict.parked`;
  - an issue's `expires_at`, `ephemeral`, `pinned`, `template` and
    `metadata`, which only `import-bd` set, are no longer shown;
    `export-bd` still writes them.
  A conflict's `field`, and an issue's states in `history`, keep the
  event log's names (`parent_id`, `due_at`).
- **The MCP `dep` and `label` tools** take `action: remove`, where they
  took `rm` (decision 88).
- **`limits:` renamed** (decision 88), with no alias: a key under its
  former name is refused as unknown. A count is `THING_per_SCOPE`, a
  size ends in `_bytes`, and a rate names its unit:

  | `memory_body` | `memory_body_bytes` |
  | `memory_tags` | `tags_per_memory` |
  | `memory_tag_length` | `memory_tag_bytes` |
  | `memory_key_length` | `memory_key_bytes` |
  | `prices` | `prices_per_project` |

  | `plan_principals` | `principals_per_plan` |

  | `open_gates` | `open_gates_per_project` |
  | `gate_checks` | `checks_per_issue` |
  | `gate_evidence` | `gate_evidence_bytes` |
  | `locks` | `locks_per_project` |
  | `lock_capacity` | `holders_per_lock` |

  | `conns` | `conns_per_server` |
  | `write_rate` | `writes_per_second` |
  | `refusal_logs` | `refusal_logs_per_minute` |
  | `open_stores` | `open_stores_per_server` |
  | `control_write_rate` | `control_writes_per_second` |
  | `conflict_age` under `limits:` | `conflict_age` at the top of the config file |
  | `due_soon` under `limits:` | `due_soon` at the top of the config file |
  | `telemetry_requests` under `limits:` | `telemetry.max_requests` |

  The `limit` attribute of `aries.limit.refusals` takes the new names,
  and the example alert rules match them.
- **The database.** Postgres 16 or newer replaces Dolt (decision 79).
  A v0.4.0 server's data is not migrated. `ariesd upgrade` takes no copy
  of the database before it migrates, as it tagged Dolt's: take a dump
  first ([Upgrades](../server.md#upgrades)).
- **`key:` in `.aries.yaml`** may name only a file inside the
  repository. A line such as `key: ~/.ssh/id_ed25519` is refused, with
  its replacement: `ARIES_KEY_FILE=~/.ssh/id_ed25519`. A CI secret that
  held a private key for `aries` to read is never read: write the key to
  a file and set `ARIES_KEY_FILE` to its path
  ([Team deployment](../deploy/team.md)).
- **Key order.** The default identities of `~/.ssh` come before
  ssh-agent's keys, so a person with several registered keys may sign
  in with a different one than before.
- **The server's account** is `aries`, and `server.user` defaults to it.
- **Commands and flags renamed** (decision 88): `aries log` is
  `aries hours` (`log` still works); `dep rm` and `label rm` are
  `remove` (`rm` still works); `admin prices` and `admin plans` are
  `admin price list|set` and `admin plan list|set`; `start --branch` is
  `start --new-branch`; `cost --by` is `cost --group-by`. `dep -t` is
  gone (`--type` stays).
- **`--json` errors** are `{"error": {"code", "message", "fix", "req"}}`,
  as the MCP server gives them, where they were `c` and `m`; and
  `version --json` gives `protocol` as a number (decision 88). From 1.0
  a JSON document only gains fields within 1.x.
- **The clock.** A server whose clock is behind its own history refuses
  to start unless told otherwise (`clock_behind`), and a usage record
  may be at most 5 minutes past the server's clock, not an hour.
- **Transport (decision 86).** HTTPS is the default, and SSH is
  off on a new server until an operator turns it on
  (`install-server.sh --enable-ssh`, then `transports: [https, ssh]`).
  `aries` uses `server.url` when `.aries.yaml` has it, and SSH
  otherwise; `ARIES_TRANSPORT=ssh` chooses SSH where both are set.

## Security changes

- **A new release signing key.** v1.0.0 is signed by a new Ed25519 key,
  generated on 15 October 2026, which replaced the former key outright
  with no release that trusts both. Clients of v1.0.0 trust only the new
  key (`internal/release/keys.go`, and the PEM in `install.sh`). The
  former key signed v0.1.0 to v0.4.0; to verify one of those downloads
  by hand, check it out at its own tag
  ([Verify a download by hand](../install.md#verify-a-download-by-hand)).
- **The license** is the GNU Affero General Public License, version 3
  only (AGPL-3.0-only), copyright Ariesworx LLC, from 15 October 2026
  (decision 82). Releases up to v0.4.0 stay under Apache-2.0, as
  published. Contributions come under a contributor license agreement,
  [CLA.md](../../CLA.md) (decision 84), so that the code can also be
  offered under a commercial license.
- **Keys.** `key:` may no longer point outside the repository, and
  `ARIES_KEY_FILE` holds a path, never a key.
- **Access ends at once.** Removing a member, a key or a principal
  closes its connections and ends its claims.
- **The server refuses a globally trusted certificate authority** for
  its account, and the findings of the stage 3a security review are
  fixed.
- **No text in telemetry.** Spans and exported log records carry ids,
  codes and small numbers, never an issue's or a memory's text, a key, a
  token or an error's message.
- **The outbox and cache** are kept in a directory that must be the
  user's alone, and the secrets lint applies before anything is queued.
- **Releases from mirrors** are checked exactly as from GitHub; no
  redirect is followed.
- **`install.sh` trusts only the key it holds** (decision 88).
  `ARIES_PUBKEY_PEM`, which replaced the release key with a warning, and
  `ARIES_BASE_URL`, which only tests used, are gone; `ARIES_RELEASES`
  names a mirror.
- **(decisions 86 and 87)** `ariesd` authenticates over HTTPS in its
  own code, where sshd did before: a proof by a key the server knows,
  bound to the connection's challenge and the server's URL, which it
  checks against its configured URLs and never against `Host`. A
  default install exposes no SSH path and nothing unauthenticated but
  `/.well-known/aries` (a test holds it). **(planned)** A security
  review of the listener and the authorization server comes before the
  release.
- **(planned, decision 87)** Tokens bound to the machine's key (DPoP),
  stored on the server only as hashes, revoked at once, with every
  connection they opened closed when they end; a token's scope decides
  what it may do, whatever the client sends.
- **(decisions 59 and 89; slice S1)** A key may have an end, after
  which it proves nothing over SSH or HTTPS, decided on the server's
  clock; sshd's line for it carries the end in UTC with its `Z`, which
  without it sshd would read in the server's own zone, reviving an
  ended key for hours west of UTC; and its open connections are closed
  at the end, which sshd does not do.
- **(planned, decision 87)** Service principals that hold no stored
  key.

## Removals

- **Dolt** (decision 79). The store, the installer, the Docker test
  server, the AppArmor profiles, CI and the guides lose Dolt, with: the
  Dolt pin and its checksums, `scripts/install-dolt.sh`,
  `internal/dolttest`, `internal/doltmetrics` and Dolt's figures in the
  status report, the tag taken before an upgrade, the commit loop, and
  the `write_id` column. The former migration sets are deleted.
- **The former names**, with no alias (decision 80).
- **The `latest` setting** (decision 88), which an operator typed in
  for `prime` to say the server was behind and which went stale
  silently. `aries upgrade --check` and `ariesd upgrade --check` ask
  the release source. A config file that still sets it is refused.
- **The MCP `cost` tool** (decision 88). People run `aries cost`; an
  agent sees an issue's cost in `show` and the window's in `digest`.
- **The step-down code** for protocol versions no release spoke
  (decisions 78 and 88), with the welcome frame's `latest` and the
  protocol's unused `IDArgs`.
- **`spike/dolt` and `spike/multidb`**, whose findings are summarized in
  `spike/postgres/RESULTS.md`.
